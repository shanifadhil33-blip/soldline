# P7 approvals engine

Exact approvals now store the full payload, sorted input references, SHA256 hashes, required roles, reversibility and expiry. Decisions use the unchanged permission matrix and scope quorum helper. Every valid approval creation, decision, confirmation, refusal, effect plan, queued job and execution result has an audit record. Repeated execution returns the first stored summary.

The old plan route now decides an existing pending plan approval. It works for real workspaces as well as demos. A run with no prepared approval returns approval not found. It does not invent an approval from the earlier sample plan label. The existing contributor 403 test still requires exactly one denied audit row and zero approvals. The old allowed audit only assertion was replaced with stronger assertions for an actual approved row and the creation and decision audits.

## Self audit

The worst silent failure is queuing work from approved inputs after those inputs have changed. In the engine, line 21 locks the approval with SELECT FOR UPDATE. Lines 63 through 66 verify the stored payload and input hashes. Line 70 performs each live read. Line 73 compares the complete recomputed input hash. Lines 74 through 77 store the readable stale reason and return on mismatch. Lines 80 through 82 repeat the expiry check. Line 87 is the first effect insert and line 90 is the first job insert. Both occur only after the live comparison succeeds.

The live reader fetches the HubSpot deal at line 21, line items at line 26, current scope at lines 13 and 14, and the ClickUp list at line 30. The test named Completes every live recheck before the first effect row or job exists checks the database inside each actual live read. All four systems must be read while both effect and job counts remain zero.

A stale reason example is HubSpot deal changed when checked at Sun, 18 Oct 2026 12:00:00 GMT. Receipt invalidation names HubSpot or ClickUp and records its observation time. Scope invalidation names the scope version and observation time. No provider response body enters a refusal message.

## Reference contract

An input reference uses system hubspot for a deal and hubspot_line_item for a line item, each with the external record id. A scope reference uses the local deal id and watches its latest scope version. A clickup reference uses the target list id. The marker is the provider modified time, scope version number, or exists for an active ClickUp list. The hash covers the validated CRM object, the scope id, version, item hash and status, or the list id and archived flag respectively. References are sorted by canonical JSON text before hashing. Callers supply all inputs on which the exact payload depends. Empty reference lists and duplicate references are refused.

The minimal creation call defaults to a human request by the authenticated member. Internal agent requests explicitly identify that request type. Creation accepts only active staff and decision eligibility uses the unchanged matrix. Members and current approver roles are loaded from the database again within the owner operation. The owner driver remains private.

Each effect contains system, location, action, records with field before and after values, amounts, and an optional full message. An email approval permits only mail effects with complete messages and irreversible classification. P7 stores and queues that exact request. P8 must execute it through the team inbox provider using createDraft then sendDraft.

## Deviations and work outside scope

The requested unit tests skill is absent from the available catalog and the repo. Existing Vitest, MSW and PGlite fixtures were used directly. The supplied acceptance excerpt was used because no plan.md exists in this repo.

Webhook and poll invalidation lives in new database triggers on durable inbound receipts and scope versions. This preserves the existing integration and scope code. A ClickUp event without a list id conservatively invalidates open approvals watching any ClickUp list in that workspace. It can require another approval for unrelated work. This is safer than leaving possibly affected work approved.

The existing ClickUp client has no get list method. The approval reader uses the existing transport with the existing list path and a validated response. No integration module was changed. Provider refusal while checking list presence marks that list stale. Provider outages and reconnect requirements refuse execution without creating effects.

The fixture connection adapter keeps provider reads, health changes and audits inside the approval transaction so there is no nested database transaction. A failed queue insertion rolls back the planned effects, jobs and provider state from that attempt, then writes a separate failed execution audit.

P8 owns the execute_approval_effect job handler, actual provider writes, final executed status and execution completion summary. Scope acceptance, cancellation and undo effects are queued requests for that handler. P7 does not send mail or carry out remote compensation. Existing workers do not claim the new execution job kind.

The supplied provider contracts have no confirmed conditional write mechanism. Data can change remotely after a live read or after P7 queues work. P8 must recheck before each real write and enforce the stored effect hash. Reversible work may only be undone under the unchanged since creation conditions from section five. These remote write and undo checks belong to P8 and were not claimed as verified here.

Production concurrency across separate database connections remains unverified because PGlite serializes transactions. The concurrent local execution test proves reuse through the named operation, while the source uses a database row lock and unique effect and job keys for production. The prior signed file retrieval, mail API contracts, identity providers, scheduling settings, demo sample replacement and deployment remain parked.

No environment file was opened or edited. No live HubSpot, ClickUp, mail or AI request, Neon connection, sign in, global installation, commit or push was performed.
